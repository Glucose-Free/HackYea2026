Architecture

Hybrid defense: a semantic checkpoint and a deterministic one

AI-based · semantic

Checkpoint 1: prompt guards

  • A local IBM Granite Guardian model answers yes/no checks: prompt injection, system-prompt extraction, role-play jailbreaks
  • Each check has its own threshold; guards run in a pipeline with per-guard timeout and fail-closed policy
  • Guard verdicts, not middleware chains: a buggy plugin can't silently skip the rest
Non-AI · deterministic

Checkpoint 2: disclosure policy

  • Per-tool role permission check
  • Each tool declares which facts it could disclose
  • A bounded Datalog engine evaluates the rules over the user's stored knowledge plus that plan, and the read runs only if no violation is derived
  • Approved facts persist per user (SQLite)

Gateway: FastAPI with an OpenAI-compatible API · Agent: Qwen 2.5 on Ollama, tools over MCP · Data server on an internal-only network.

Design decision

We decide before reading the data, so a refusal can't leak it

% the whole aml_contact rule
violation(U, C, aml_contact) :-
    knows(U, C, aml_review,   Status),
    knows(U, C, contact_data, Value).

Rules are plain JSON, edited by the security team. No code changes, no redeploy.

The trade-off we chose

Before a fetch, the engine doesn't know which customer an AML case names. If it peeked at the secret to decide, the refusal itself would reveal it.

So it plans with unknown values and blocks conservatively.

cost  a user who knows any customer's contact is refused every AML summary.

gain  no side channel through denials.

Centralized policy

Policy is config: change rules and guards without a redeploy

# config/gateway.ollama.toml
[[user_input.guards]]
instance_id = "semantic_safety"
type        = "jev_semantic"
mode        = "enforce"   # or "monitor"
timeout_ms  = 30000
on_error    = "refuse"    # fail closed

[[user_input.guards.settings.checks]]
label = "prompt_injection"
refuse_threshold = 0.5

Adjustable strictness

  • enforce vs monitor per guard: trial a new check on live traffic before it blocks
  • Per-check refusal thresholds
  • Fail closed or open per guard
  • Hot reload: edits apply on the next request; an invalid file is rejected and the last working version stays active
  • Every config version is kept and recorded on each audited request

Implementability

Pluggable by design: new domains, guards and models drop in

New guard

One class with check(conversation), registered as a Python entry point. Shows up in config, audit and dashboard.

New data domain

Tools declare the facts they disclose. AML and transactions share one engine without the core knowing either.

Any model

Any OpenAI-compatible endpoint for the agent. Swappable adapters for the guard model. Local Ollama by default: no paid APIs.

One command

docker compose up brings up chat, gateway, data server and models.

Standard protocols

OpenAI Chat API in, MCP over streamable HTTP out. Drop it in front of an existing agent.

Network isolation

The data server lives on an internal network that only the gateway can reach.
